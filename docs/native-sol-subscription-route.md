# Native Sol subscription routing

Bulk model installation sends model.set with openai/gpt-6.1-sol, even when the agent uses ChatGPT OAuth. The compatibility metadata must consult the authoritative runtime auth store instead of inferring subscription use only from a codex/ prefix.

A generated openai-responses model API forces API-key auth. With a healthy OAuth profile and an explicit stored profile order, OpenClaw filters out the incompatible profile and reports: "Explicit auth order for openai has no usable profiles." This error does not by itself mean tokens are missing or expired. Reasoning high is unrelated.

The relay now reads shared machine-state auth, agent SQLite, or legacy auth according to runtime ownership. Retired legacy credentials are ignored. Identity-only and token-sharing OAuth are not inferred as subscriptions. Existing explicit provider/model API, endpoint, credential, header, and environment endpoint overrides remain authoritative.

## Generated provider overrides after doctor migration

Backend provisioning historically generated `models.providers.codex` (and openai)
with exactly `{baseUrl: BACKEND_BASE_URL + "/api/v1/relays/openai/v1", models: []}`.
OpenClaw doctor can migrate that codex row into openai. The resulting provider
endpoint alone forces API auth, even with valid saved subscription credentials.

Both model.set and modelAssignment.set now reconcile these exact empty generated
rows before adding Sol compatibility metadata whenever an OpenAI model is requested
and the authoritative runtime store contains a subscription. They inspect both
openai and codex so subsequent alias migration cannot recreate the override.
No token, profile order, auth database, CLI auth or environment is rewritten.

Ownership is deliberately narrow: the endpoint must equal the current relay
BACKEND_BASE_URL (trimmed, without trailing slashes) plus the backend's exact
/api/v1/relays/openai/v1 suffix. No host substring matching or public-host allowlist
is used. The provider must contain ONLY baseUrl and an empty models array.
Custom URLs, headers, API/auth fields, model rows, unknown provider fields and
local-proxy rows are preserved in full. Any OpenAI/Codex API key in the authoritative
store, config auth profiles or environment blocks cleanup; environment base URL
settings also block it. Other providers are untouched. A historical backend URL,
missing deployment authority or any ambiguous row needs explicit operator review,
not speculative cleanup. A model alias alone does not prove a saved subscription.

This is model-action reconciliation, not a background watcher. Later backend
reprovisioning can reintroduce a generated row; reapplying a model action safely
reconciles it again. Existing nonempty generated model rows are not inferred to be
owned: explicit per-model APIs remain authoritative.

## Existing affected model rows

The Sol compatibility fix prevents incorrect metadata creation; it deliberately does not silently overwrite an existing explicit model API. A prior generated row is indistinguishable from a user-authored identical override without external provenance.

For an already affected agent, first verify the model-change action and sanitized current config establish that the incorrect Sol row was generated by this relay. Back up config, confirm the exact current row and absence of custom routing, then explicitly repair only that known generated API to openai-chatgpt-responses (or remove only that known generated row and reassign with the fixed relay). Preserve auth credentials, profile order, other models and endpoints. Do not clear auth or force a new login to hide a route incompatibility. Perform this only within the operator-authorized agent scope.

## Verification

Regression coverage includes shared and agent SQLite ownership, stale legacy JSON, future and expired subscription credentials, explicit routes, and unrelated Codex fallbacks. Run npm test, npm run build, npm run lint. Loopback HTTP tests may require NO_PROXY=127.0.0.1,localhost in proxied environments.

A disposable dev-api OC 2026.9.8 fixture reproduced the exact user-visible error through the deployed webchat after the dashboard-equivalent POST with thinkingDefault high and synthetic OAuth state. Native runtime route-selection checks can isolate this failure without valid provider credentials; they are not proof of successful external ChatGPT inference. Never copy unrelated live credentials into a test fixture.

For an offline installed-runtime regression, run:

```
npm run build
node scripts/prove-managed-subscription-route.mjs
```

The script uses isolated temporary state and synthetic credentials written through
the installed public auth SDK. It reproduces the exact explicit-order rejection
for migrated managed provider rows, invokes the real relay model.set (only service
control is stubbed), then verifies the installed runtime selects the subscription
route for GPT-5.4 and Sol. Auth database bytes and config profile order must remain
unchanged. No manual intermediate config repair, external inference, real login
or live service changes occur. The diagnostic discovers private runtime resolver
exports by source name and fails if ambiguous; production code does not use those
private exports. This proves local routing, not live ChatGPT inference.
